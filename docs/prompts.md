# Prompts

The app uses one production prompt. The experiment compares that idea with a shorter prompt that does not include the schema.

Both prompts ask for a single read-only SQLite `SELECT`. Neither prompt includes rows from the database. The model only sees the question and, in the schema-aware prompt, the table and column names.

## Production prompt

`sql_engine.py` sends this prompt to `qwen2.5-coder:3b` with temperature 0. The schema block is filled in by `get_schema()` at the moment the question is asked.

```text
You are an expert SQLite SQL assistant.

Generate exactly one valid SQLite SELECT query
to answer the user's question.

RULES:
1. Use only the provided tables and columns.
2. Use correct JOIN relationships.
3. Never invent table or column names.
4. Generate only SELECT statements.
5. Never generate INSERT, UPDATE, DELETE,
   DROP, ALTER, CREATE or other modifications.
6. Use AND when all conditions must be true.
7. Use OR when either condition can be true.
8. Preserve the logical operator in the question.
9. "Both" means AND.
10. "Either" means OR.
11. Use SUM() for total sales and total profit.
12. Use COUNT() to count records.
13. Use GROUP BY for grouped results.
14. Use ORDER BY and LIMIT for top or bottom results.
15. Return only SQL without Markdown or explanations.

DATABASE SCHEMA:
<live table and column list, plus the relationships below>

USER QUESTION:
<the question typed in the app>

Generate the SQLite query:
```

The relationship text added to the schema is:

```text
DATABASE RELATIONSHIPS:
- orders.customer_id = customers.customer_id
- payments.order_id = orders.order_id
- orders.product_name = products.product_name

COLUMN MEANINGS:
- customers.region: Customer's region.
- customers.state: Customer's state.
- orders.region: Region recorded for an order.
- orders.profit: Profit generated by an order.
- orders.sales: Revenue generated by an order.
- products.unit_price: Product unit price.
```

Why these rules are there:

- Rules 1–3 stop the model from inventing a table such as `sales`, which is what the basic prompt did in the experiment.
- Rules 4–5 match the checker in `execute_sql()`. A modifying statement is rejected even if the model writes one.
- Rules 6–10 keep `AND` and `OR` from being swapped. "Both" and "either" are called out because small models often turn them into the wrong join condition.
- Rules 11–14 name the exact aggregate pattern used by the sample questions: `SUM` for money, `COUNT` for rows, `GROUP BY` for a breakdown, and `ORDER BY ... LIMIT` for a highest or lowest result.
- Rule 15 keeps the reply as SQL so the parser does not have to read a paragraph. The engine still strips a ` ```sql ` fence if the model adds one.

The request uses `temperature: 0`, at most 250 generated tokens, and a 2048-token context. The same model is kept loaded for 10 minutes (`keep_alive: 10m`) so the next question does not reload it.

## Experiment prompts

`prompt_experiment.py` asks the same five questions twice.

The basic prompt only says "sales database." It does not list tables or columns:

```text
Convert the user's question into one SQLite SELECT query
for a sales database.

Return only SQL. Do not include markdown or explanations.
Do not generate INSERT, UPDATE, DELETE, DROP, or other
data-modifying statements.

Question: <question>

SQL:
```

The schema-aware prompt includes the live schema and a shorter rule list: use only those tables and columns, use exact names, use `GROUP BY` when the question asks for a breakdown, and use `ORDER BY` plus `LIMIT` for a highest or lowest result.

On the original 10-order database, saved in `prompt_experiment_results.csv`:

| Method | Passed | Accuracy | What went wrong |
| --- | --- | --- | --- |
| Basic | 1 of 5 | 20% | Four queries used a table named `sales` and columns that do not exist |
| Schema-aware | 5 of 5 | 100% | Every query used `orders` and the real column names |

The one basic success was `SELECT COUNT(*) AS total_orders FROM orders`, because that question can be answered without knowing the other columns. The schema is what stops the model from guessing `sales_amount`, `product_id`, and `cost`.

## What the checker does after the prompt

`execute_sql()` does not trust the prompt. It parses the reply with SQLGlot and rejects it unless all of these are true:

- There is exactly one statement.
- The statement is a `SELECT`, or a `UNION`, `INTERSECT`, or `EXCEPT` of selects.
- Every real table is one of `orders`, `customers`, `products`, or `payments`.
- The query returns columns.

SQLite then runs with `PRAGMA query_only = ON`, and the app keeps the first 100 rows.
